# franchise-rag 설계

이 문서는 franchise-rag의 데이터 수집 경로, 조항 표준화 방식, RAG 질의응답 구조, 그리고 만들면서 내린 판단을 정리한다.
사용법은 [README](../README.md)에 있다.

> 코드 주석에 나오는 「작업로그 (N)」은 개발 중 쓴 내부 기록의 번호다. 그 기록은 공개하지 않고, 결론만 이 문서에 옮겼다.

---

## 1. 설계 원칙

| 원칙 | 뜻 |
| --- | --- |
| 숫자는 LLM이 만들지 않는다 | 가맹비·보증금·매출액 같은 구조화 값은 데이터에서 그대로 꺼내 꽂는다. LLM이 설명 문장을 쓰더라도 문장 속 금액을 원본과 전부 대조하고, 하나라도 안 맞으면 LLM 없이 만든 문장으로 바꾼다 |
| 추측하지 않는다 | 브랜드를 못 찾으면 비슷한 걸 골라 답하지 않는다. 「이름을 모름」「이름은 있지만 데이터 없음」「동명이인」을 구분해 알리고, 후보는 사용자가 고르게 한다 |
| 출처를 붙인다 | 모든 답에 `[브랜드-카테고리-조항명]` 출처와 원문 위치를 붙인다. 화면에서 출처를 누르면 원문 조항·표를 본다 |
| 모르면 모른다고 한다 | 단위를 못 찾은 금액은 「단위 미확인」, 별첨으로 빠진 내용은 「원문 별첨 참조」, 위반 이력 문구가 모순되면 `null`로 둔다 |

## 2. 데이터 소스

공식 문서가 거의 없어서 실호출로 확인한 내용이다.

### 2.1 정보공개서 목록·본문 API (핵심)

- 공정거래위원회 가맹사업거래 시스템 자체 API. 키는 `franchise.ftc.go.kr`에서 따로 발급한다(data.go.kr 키와 다름).
- 가이드: `https://franchise.ftc.go.kr/openApi/guide.do`
- Base: `https://franchise.ftc.go.kr/api/search.do`

| 기능 | 파라미터 | 비고 |
|---|---|---|
| 목록 `type=list` | `yr`(필수), `serviceKey`, `pageNo`, `numOfRows`, `viewType` | `item{jngIfrmpSn, corpNm, brandNm, brno, jngIfrmpRgsno}` |
| 본문 `type=content` | `jngIfrmpSn`(필수), `serviceKey` | 조항별 `<section><hN title=".." attr="..">…<table>` |
| 뷰어 | `/api/viewer.do?jngIfrmpSn=..` | 원문 대조용 |

- 목록 API는 `yr` 말고 어떤 검색 파라미터도 받지 않는다(brno·brandNm 등은 무시됨). 그래서 연도별 목록을 통째로 받아 `brno → jngIfrmpSn` 색인을 만든다.
- 본문 응답은 표준 XML이 아니다(`<xml version=...>`로 시작, 닫히지 않는 태그). ElementTree 대신 헤딩 위치로 섹션을 자르고, 표는 BeautifulSoup(lxml)으로 읽는다.
- 레이트 리밋은 문서에 없다. 호출 간격 0.35초로 시작했다.

### 2.2 브랜드 목록

- data.go.kr `FftcBrandRlsInfo2_Service/getBrandinfo`. 브랜드 12,498건(`brandMnno`, `brandNm`, `corpNm`, `brno`, 업종 등).
- 목록 API와는 `brno`(사업자등록번호)로 잇는다.

### 2.3 커버리지

목록 API로 찾을 수 있는 정보공개서는 브랜드 목록보다 훨씬 적다(매칭률 약 30%). 처음에는 API 고장으로 보고 웹 스크래핑으로 우회했지만(캡챠에 막힘), 실제로는 시스템에 등록된 유효 정보공개서 수 자체가 적은 것이었다. 결론: **API로 확보되는 브랜드(약 2,400개)만 쓰고, 없는 브랜드는 「데이터 없음」으로 표시한다.**

## 3. 수집과 표준화 파이프라인

```
01_fetch_disclosure_lists.py   연도별 목록 → brno 색인
        ▼
02_fetch_disclosure_content.py 브랜드 → 정보공개서 매칭 → 본문 XML 저장
        ▼
03_extract_clauses.py          attr 코드로 조항 선별 · 표 복원 · 금액 정규화 → clauses.jsonl.gz
        ▼
11_build_embeddings.py         서술형 조항만 KURE-v1 임베딩 → Chroma
```

### 3.1 브랜드 ↔ 정보공개서 매칭

한 사업자등록번호에 브랜드가 여러 개인 경우가 있다. 처음에는 「그 해 후보가 하나면 이름 대조 없이 채택」해서, 전혀 다른 브랜드 문서가 붙은 경우가 5.9% 있었다. 지금은 **모든 연도 후보를 모은 뒤 브랜드명(별칭 포함)이 정확히 같은 것만** 채택하고, 없으면 매칭 실패로 둔다. 전수 검증 결과 불일치 0건.

### 3.2 조항 분류: 공식 attr 코드

본문 헤딩에는 공정위가 붙인 고정 코드(`attr`)가 있다. 브랜드·연도와 상관없이 같은 항목이면 같은 코드다(헤딩 24만여 개 전수 확인, 고유 코드 110개). 제목 키워드 매칭 대신 이 코드로 분류한다. 110개 중 비교에 쓰는 38개만 골라 `section_schema.py`에 `{attr: (category, canonical_title, chapter)}`로 적었다.

| 구분 | 카테고리 | 처리 |
|---|---|---|
| 구조화 | 가맹비/가맹금 · 보증금 · 교육비 · 로열티 · 평균매출액 · 행정처분 | 값을 직접 조회 |
| 서술형 | 계약해지 · 필수구입물품 · 영업지역 · 소송/법위반 · 위약금/손해배상 | 벡터 검색 |

키워드 방식이었을 때는 「가맹금 예치기관」(은행 안내 문구)과 「최초 가맹금」(실제 금액)이 한 카테고리로 섞였다. 코드 방식으로 바꾸며 예치기관 코드는 뺐다.

### 3.3 표 복원과 금액 정규화

- **병합 칸:** colspan·rowspan을 펼쳐 완전한 격자로 만든다. 펼치지 않으면 rowspan 아래 행의 칸이 왼쪽으로 밀려 금액이 다른 열로 붙는다.
- **여러 줄 머리글:** 금액이 나오기 전까지의 행을 모두 머리글로 보고 합친다(예: 「타입별 금액 / BSK」, 「연간 평균 매출액 / 상한 / 면적 3.3㎡당」).
- **단위:** 칸에 단위가 없으면 표 캡션·머리글의 「단위: 천원」을 적용한다. 이걸 놓치면 금액이 1,000배 틀린다. 섹션에 표가 여럿이면 표마다 바로 위 문단에서 단위를 따로 읽는다. 끝내 못 찾으면 `amount_unit_detected: null`(약 8~10%).
- **표 소속:** 표가 여럿인 섹션은 금액마다 `table_context`(예: 「(가) BSK」)를 남긴다.
- **위반 이력:** 시정조치·민사소송·형의 선고 섹션에서 `violation_flag`(있음/없음/null)를 뽑는다. 문구가 서로 모순되면 null.

출력 한 줄(조항 하나): `brandMnno`, `brandNm_matched`, `attr`, `category`, `canonical_title`, `text`(표 제외 본문), `tables`(격자), `amounts`(`label`, `column`, `amount_won`, `raw`, `table_context`), `amount_unit_detected`, `violation_flag`, `attachment_refs`.

## 4. RAG 질의응답

`backend/scripts/rag/`는 웹 프레임워크에 의존하지 않는 모듈이고, FastAPI는 `pipeline.answer_question()` 하나만 부른다.

```
질문
 ▼
0. 브랜드 정규화 (brand_match)   이름·별칭·괄호 축약형 → brandMnno
 ▼
1. 슬롯 추출 (nlu)              LLM 1회: intent · brands · category · canonical_title
 ▼
2. 조회 (retrieval)             구조화: 값 직접 필터 / 서술형: 브랜드별 필터 후 dense 검색
 ▼
3. 답변 조립 (answer, total_cost)  구조화: 그룹핑 → LLM 설명 → 숫자 검증 → 실패 시 템플릿
                                 서술형: 원문(+표)만 근거로 LLM 요약, 출처 태그
```

### 4.1 브랜드 해석

- 이름 인식과 데이터 보유 여부를 따로 판정한다. 결과는 `unresolved`(이름 모름) · `no_data`(이름은 있음) · `ambiguous`(동명이인)로 나뉘고 안내 문구가 다르다.
- LLM이 브랜드명을 잘못 옮기면(축약, 한자 섞임) 질문 원문에서 등록명을 다시 찾는다.
- 완전히 못 찾으면 `difflib` 유사도로 후보를 버튼으로 보여 준다. 숫자 브랜드(「101프렙」을 「일공일 프렙」으로 입력)는 LLM에게 실제 등록명 목록 안에서만 고르게 하고, 목록 밖 답은 버린다. 최종 선택은 항상 사용자가 한다.
- 법인이 다른 동명이인은 「법인명, 개시연도」를 붙여 구분한다.

### 4.2 비교 질문

전체를 검색한 뒤 브랜드로 거르면 글이 많은 브랜드가 상위를 독차지한다. 그래서 **브랜드마다 따로 검색해서 합친다.** 금액 비교는 벡터 검색 없이 값을 바로 꺼낸다.

### 4.3 총창업비용

여러 표의 「합계」 행(라벨이 총계·합계와 정확히 같을 때만)을 모아 계산한다. 예치가맹금은 최초 가맹금 + 보증금을 다시 합친 값이라, 예치가맹금이 있으면 최초 가맹금은 더하지 않는다(이중 계산 방지). 매장 타입이 여럿이면 하나로 합치지 않고 타입별로 보여 준다. 계산 가능 브랜드 약 92%.

### 4.4 알려진 우회

chromadb 1.5.x에서 벡터 검색과 메타데이터 필터를 같이 쓰면 `Error finding id`로 실패한다. 후보를 `get(where=...)`로만 가져오고, 그 자리에서 다시 임베딩해 코사인 유사도를 직접 계산한다. 브랜드 하나의 후보는 수십 건 이하라 비용이 작다.

## 7. 한계

- 목록 API에 없는 브랜드(일부 대형 브랜드 포함)는 데이터가 없다.
- 단위가 문서에 아예 없는 금액은 단위를 확정하지 못한다.
- 행이 100개를 넘는 일부 표에서 순번이 금액으로 잡히는 경우가 있다.
- 「정보공개서에 적히지 않은 항목」 안내는 서술형 답변에만 붙는다.
- 답변은 한 번에 나온다(토큰 스트리밍 없음).
